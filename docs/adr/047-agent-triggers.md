# ADR-047: Agent triggers: events that start an agent's work

**Status:** accepted (approved by the product owner, 2026-10-31)
**Date:** 2026-10-31

## Context

ADR-046 made agents users of the runtime: an agent connects over MCP as
an agent identity, reads pipelines and runs, works out why a run failed
(`explain_run`), and proposes the fix as a change request a person
applies. Everything an agent needs to *do* the work exists. Nothing tells
it *when*.

Today an agent acts only when a person starts it: someone opens a desktop
assistant, an IDE, or a script, and asks. A run that fails at 03:00 waits
until a person notices it, and then the person starts the agent. The loop
"a step fails, an agent finds out why and proposes the fix, a person
applies it in the morning" needs one more piece: the failure has to reach
the agent on its own.

What exists, and why none of it is that piece:

- **Lifecycle hooks** (`Pipeline.Hooks`: `on_start`, `on_success`,
  `on_failure`, `on_node_failure`; `Runner.fireHook`, `engine/runner.go`).
  One unsigned POST, sent by whichever process ran the pipeline, with a
  10 second timeout and no retry. A receiver that is down, slow, or
  restarting loses the event for good, and nothing records that it was
  lost. A receiver cannot tell a real event from a forged one. That is
  acceptable for a Slack message; it is not acceptable for the thing that
  starts an agent.
- **Alerts** (`models.Alert`, `store.CreateAlert`) are durable and
  readable, but addressed to people: an inbox, an assignee, read state.
- **The notify node** sends a message as a step of a pipeline: it runs
  only when the pipeline reaches it, so it says nothing about the run
  failing before it.
- **The run event log** (`models.RunEvent`, `store.AppendEvent`) is the
  durable, append-only record of every run's lifecycle, including the
  terminal outcome (`run.terminal` with its status: `success`, `failed`,
  `blocked`).
  It is written wherever a run executes, remote workers included, and it
  survives restarts. It is the right *source*; it has no way to *deliver*
  anything.

Two constraints shape the delivery:

- **An agent may not be reachable.** A hosted agent has a URL. An agent
  on a laptop, in a CI job, or behind a NAT does not, and must be able to
  ask instead of being called.
- **A trigger must not widen what an agent can do.** ADR-046's rules hold:
  an agent acts with its own token, never above its owner, never reading a
  secret, and never applying a change. A trigger only says "this happened";
  the agent then works through the same MCP tools and permission checks as
  when a person starts it.

## Decision

An **agent trigger** subscribes an agent identity to run events. When a
matching event is recorded, Brokoli **delivers** it durably, by a
**signed webhook** to the agent's URL or through a **feed the agent
pulls**, and the agent does its work over MCP with its own token. The
event carries identifiers and context, never a credential.

### 1. Triggers

A trigger belongs to a workspace and names:

- **the agent** it starts (an agent identity, ADR-046 section 2);
- **its scope**: one pipeline, or every pipeline in the workspace;
- **the events** it wants (section 2);
- **how it is delivered**: a webhook URL, or the pull feed;
- **a cooldown** (default 30 minutes) per pipeline and event type: after a
  delivery, the same trigger does not deliver the same event about the
  same pipeline again until it passes. A pipeline failing every five
  minutes produces one delivery, not twelve an hour; the run page still
  shows every failure. (Amended in phase 2: the cooldown was per pipeline,
  which would have hidden the `run.recovered` after a delivered
  `run.failed`. Test events do not count toward it.)

Creating or changing a trigger needs permission to manage the agent: its
owner, or someone who may manage users. A webhook trigger's **signing
secret** is generated by Brokoli and shown once. Signing needs the secret
itself, so it is stored encrypted with the server's key
(`crypto.Config.Encrypt`, as connection credentials are), never returned
by the API, and used only by the dispatcher. It is not a Brokoli
credential and grants nothing.

A trigger never fires for a pipeline the agent cannot see. The check is
made **at delivery**, with the agent's permissions as they are then (its
role, within its owner's current permissions), so demoting the owner or
disabling the agent stops its triggers without anyone editing them.

### 2. Events

The first event types come straight from the run event log:

| Event | When |
|---|---|
| `run.failed` | a run ends with status `failed`, including when a quality check or contract gate blocks it (the event names each failed step and its type) |
| `run.blocked` | a run did not start because its dependencies were not satisfied (status `blocked`) |
| `run.recovered` | a run succeeds after the previous run of the same pipeline did not |

`run.recovered` lets an agent close the loop: it learns that the fix it
proposed, once applied, worked.

A distribution can add event types through the same extension point it
uses for MCP tools (`mcpserver.Register`'s pattern): for example a missed
deadline, where the deadline is tracked by that distribution. Added types
follow every rule here: durable delivery, the visibility check, the
cooldown.

### 3. Durable delivery

Delivery is **at least once**, and it cannot be lost by a restart:

- The scheduler's leader (the replica `LeaderElector` elects; one at a
  time) reads the run event log from a stored cursor, matches terminal
  events against enabled triggers, and writes one **delivery** row per
  match, in the same transaction that advances the cursor. A run that
  finished on a remote worker is covered, because its events are in the
  log like any other.
- A **dispatcher** on the leader sends due deliveries and records each
  attempt: when, the HTTP status, how long it took, and the first bytes
  of the answer. A delivery that is not answered with 2xx within 10
  seconds is retried with capped exponential backoff and jitter (the
  shape the REST source's page retries use) for up to 24 hours, then
  marked **failed**.
- Each delivery has a stable id. An agent that receives the same id twice
  ignores the second.
- Outbound requests use the operator's network policy (`netguard`), as
  hooks already do: a trigger cannot be pointed at internal addresses the
  policy forbids.

### 4. Signing

Webhook deliveries follow the **Standard Webhooks** specification
(standardwebhooks.com) rather than a scheme of our own, so receivers can
use an existing library in any language:

- headers `webhook-id` (the delivery id), `webhook-timestamp` (Unix
  seconds) and `webhook-signature` (`v1,` + base64 of HMAC-SHA256 over
  `id.timestamp.body` with the trigger's secret);
- a receiver rejects a timestamp more than five minutes away from its
  clock, which bounds replay;
- secrets rotate with an overlap: during rotation both the old and new
  signatures are sent, separated by a space, as the specification allows.

### 5. The event

```json
{
  "type": "run.failed",
  "id": "evt_01a1...",
  "occurred_at": "2026-10-31T03:12:09Z",
  "workspace_id": "...",
  "agent": "triage-bot",
  "pipeline": { "id": "...", "name": "orders_daily" },
  "run": {
    "id": "01a1...",
    "status": "failed",
    "failed_nodes": [{ "name": "Fetch orders", "type": "source_api" }],
    "error": "GET https://shop.example.com/v2/orders: 404 Not Found"
  },
  "next": {
    "mcp": "https://brokoli.example.com/api/mcp",
    "suggested_tool": "explain_run",
    "run_url": "https://brokoli.example.com/runs/01a1..."
  }
}
```

- **No credential, ever.** The agent authenticates its MCP calls with the
  token it already holds. A leaked or forwarded event lets nobody do
  anything.
- **Redacted.** The error text passes through the same redaction as every
  MCP result (`pkg/mcpserver`): passwords in URLs, `Bearer` and `Basic`
  credentials, secret-named fields.
- **Bounded.** The error is cut at 2,000 characters, as MCP results are.
  The event says what happened and where to look; `explain_run` gives the
  rest.

### 6. The pull feed

For an agent without a URL, a trigger delivers to a feed the agent reads
with its own token:

- `GET /api/agents/me/events?after=<cursor>` returns that agent's
  pending deliveries, oldest first, and an MCP tool `next_events` does the
  same, so an agent client can poll between tasks.
- Reading with a cursor acknowledges everything before it. Unread
  deliveries are kept for 7 days, then marked expired.

The same delivery rows back both modes, so the delivery log, the
visibility check and the cooldown are identical.

### 7. Seeing and testing it

- Each trigger has a **delivery log**: every delivery, every attempt,
  status and timing, with a button (and API call) to redeliver one.
- **Send a test event** delivers a synthetic `run.failed` marked
  `"test": true` from a pipeline the agent can see, so a receiver can be
  wired up without waiting for a real failure.
- Runs show which agent was notified about them, linking the run page to
  what the agent then proposed.

### 8. The reference triage agent

Core ships a small reference agent (in `examples/agents/triage`) that
does the whole loop, so a team can see it work in minutes and replace the
parts it wants to:

1. verifies the signature (or polls the feed);
2. connects over MCP with its agent token and calls `explain_run`;
3. when the cause is in the pipeline definition, drafts the fix and calls
   `propose_change`, with the description `propose_change` asks for (why,
   what changes, what to check);
4. otherwise reports what it found and stops, proposing nothing.

It uses a model provider the operator configures. It runs as a small
service, or as a scheduled job in CI using the pull feed. It never
applies a change; nothing in this ADR lets an agent apply one.

## Consequences

### Positive

- The loop runs without a person starting it: a failure at night is
  investigated at night, and a person wakes up to a proposed fix with its
  reasons, not to a red dashboard.
- Delivery is durable and visible, which hooks never were: a delivery
  that cannot be made is retried, and then shows as failed, instead of
  vanishing.
- Nothing about what an agent may do changes. A trigger starts the work;
  the work is still MCP calls with the agent's token, checked as before.
- Standard Webhooks signing means receivers need no Brokoli-specific
  code, and the pull feed covers agents that cannot be reached.

### Negative

- A new outbox (deliveries and attempts) with retention to run: deliveries
  are kept 30 days, then pruned.
- The leader now dispatches. A leader change resumes from the stored
  cursor and the due deliveries; a delivery being sent at the moment of
  the change may be sent twice, which the delivery id makes harmless.
- Agents act on real failures with real model calls. Cost and noise are
  bounded by the cooldown and the scope, not eliminated; a workspace-wide
  trigger on a flaky workspace still fires often.

### Deferred

- **Moving lifecycle hooks onto the same delivery** (signing, retries,
  log). Worth doing; it changes an existing contract, so it gets its own
  decision.
- **Node-level events** (`node.failed` mid-run). Terminal events first;
  an agent acting on a run still in progress needs more thought.
- **Policies that let an agent's proposal apply itself** for narrowly
  defined changes (a retry count, a timeout). Out of scope: every change
  is still applied by a person.
- **An agent previewing its own proposal** with sinks held back. Separate
  decision, because a preview runs proposed code.

## Alternatives considered

- **Make lifecycle hooks reliable and point them at agents.** Hooks are
  per pipeline, owned by whoever edits the pipeline, sent from the process
  that ran it, and carry no agent identity; making them durable means
  moving their sending off the runner anyway. Agents need workspace scope,
  a visibility check against the agent, and a pull mode, which hooks would
  grow awkwardly.
- **Alerts with an agent as the assignee.** Alerts are a person's inbox,
  with read state and ownership semantics that do not fit an agent, and
  they deliver nothing outward.
- **Agents poll the runs API.** Works without any change and is what an
  agent can do today, but every agent reinvents cursors, filtering and
  visibility, and polling often enough to be useful is wasteful. The pull
  feed is that, done once.
- **Send the agent's token in the event, so the receiver need not hold
  one.** A webhook URL is configuration anyone editing the trigger can
  change; a token in the payload would be a credential sent to whatever
  it points at. The receiver holds its token; the event holds none.
- **A scheme of our own for signing.** Standard Webhooks already defines
  the headers, the replay window and rotation, and has libraries in most
  languages; a custom scheme would make every receiver write its own.

## Follow-ups

- **Phase 1:** triggers and deliveries in the store (SQLite and
  Postgres), the leader's matcher over the run event log, the dispatcher
  with retries and Standard Webhooks signing, `run.failed` and
  `run.blocked`, the delivery log and redelivery, the API, and
  `brokoli agents trigger ...` in the CLI.
- **Phase 2:** the pull feed (`GET /api/agents/me/events`, the
  `next_events` MCP tool), `run.recovered`, the test event, and the
  reference triage agent in `examples/agents/triage` with its docs.
- **Phase 3:** the UI: triggers on the agent's page and the pipeline's
  settings, the delivery log, and "agent notified" on the run page; the
  distribution extension point for added event types.
- **Docs:** `docs/agent-triggers.md`, and the receiver side (verifying a
  signature, acknowledging the feed) in `docs/mcp.md`'s neighborhood.
